# Code Style Guide

## C#

### Sorting

Members of a C# `class`, `struct`, `interface` and `record` are sorted by the following groups.
Groups are separated from each other by a line break.

1. Constants
2. Static fields
3. Other fields
4. Properties
5. Events
6. Constructors
   - Grouped by keyword in order of `static`, `public`, `internal`, `protected`, `private` followed by constructors without keyword
   - Groups are sorted by number of parameters in ascending order
7. Methods

### Test methods

- Test method names should use [snake case](https://en.wikipedia.org/wiki/Snake_case) pattern.

  > The Test Explorer replaces underlines with spaces because of [`our configuration`](https://gitlab.com/vicione-oss/vicione/suite/suite/-/blob/6fc3db74e4f7627ead5d562436e588ef44089165/xunit.runner.json#L4) of [`methodDisplayOptions`](https://xunit.net/docs/runsettings#MethodDisplayOptions). As a result, test names like `Should_return_access_level_requirement` are displayed as formulated sentences like `Should return access level requirement`.

## Code comments

Comments are read far more often than they are written, and a redundant or stale comment costs more than no
comment at all. These rules apply to every hand-written `*.cs` and `*.razor` file in the solution.

**Out of scope:** generated and scaffolded code is never edited by hand — EF Core migrations
(`*/Migrations/*`), designer files (`*.Designer.cs`), anything under `obj/` or `bin/`, and any file carrying
an `<auto-generated>` header. Leave their comments exactly as the tool emits them.

### The two principles

**1. Write down only what the code cannot say.** The code already records *what* happens. A comment earns its
place by adding something the reader cannot get from the code: a reason, a constraint, a trade-off, a
non-local consequence, or a pointer to a decision made elsewhere.

**2. A good name is the better comment.** Before writing a comment, check whether renaming removes the need
for it. A rename helps every caller; a comment helps only the reader standing in front of it.

```csharp
// Bad - the comment carries the meaning, the code does not
// filter out fieldsets not filled and remove duplicates
state.DnsDetails = [.. state.DnsDetails.Where(d => !string.IsNullOrWhiteSpace(d.IpAddress)).Distinct()];

// Good - the name carries the meaning, no comment needed
state.DnsDetails = state.DnsDetails.WithoutEmptyOrDuplicateEntries();
```

### Keep these comments

Tighten the wording, but never delete the substance:

- **Why a decision was made**, especially when the obvious alternative was rejected — including references to
  an ADR, an issue, a spec section or a vendor bug.
- **Ordering and placement constraints** that the code cannot express, e.g. why a filter must sit inside
  another one.
- **Platform and third-party quirks**, e.g. behaviour of MassTransit, EF Core or the Edge-S target that
  surprises the reader.
- **Deliberate no-ops**, e.g. why a caught exception is swallowed.
- **Warnings to the next maintainer**, e.g. "add new fields here too" on a mapper.

### Delete these comments

- Anything that narrates the next line: `// open combobox` above `combobox.Open()`.
- Anything that restates the signature: `/// Gets or sets the user name.` on `UserName`,
  `/// <param name="cancellationToken">A token to monitor for cancellation requests.</param>`.
- Empty XML tags: `<returns></returns>`, `<param name="x"></param>`, `<summary></summary>`.
- Commented-out code. Git remembers it. If markup is parked for a feature that is not implemented yet, leave
  **one** comment saying so — not forty lines of dead markup.
- Separator banners (`// -----`), file headers, `#region` labels, and change logs inside files.
- Questions to yourself: `// Extra State for module process to start?`. Answer it, or open an issue.

### How to write one

| Rule | |
|---|---|
| Form (`///` vs `//`) | A comment describing a declaration is an XML doc comment. Plain `//` is for statements inside a body. See [XML documentation](#xml-documentation). |
| Language | en-US only. No German. |
| Voice | Impersonal and present tense. Not "we clear the cache" but "the cache is cleared" or "clearing the cache releases the file lock". |
| Tone | Neutral and factual. No exclamation marks, no emoticons, no humour at the code's expense. |
| Form | Full sentence, capitalised, ending with a period. Structural markers (`// Arrange`, `// Act`, `// Assert`) are the exception. |
| Length | One comment line stays under 140 characters; one comment block stays under 6 lines. |
| Overflow | Longer rationale belongs in `docs/` or an ADR, with a one-line pointer from the code. |
| Whitespace | No trailing whitespace on a comment line. |

### XML documentation

The suite's public surface is the **`suite-sdk`** repository, and it is documented under that repository's
own rules. Inside this repository XML documentation is **optional**: write one when it says something the
signature does not, skip it when it would only restate the member name.

What is *not* optional is the form:

> **When a comment describes a declaration, it is an XML doc comment.** A `//` line directly above a type,
> method, property, field or event belongs in `///`. Plain `//` is for statements inside a body.

XML docs travel — IntelliSense, generated documentation, and the SDK's consumers all read them, and a plain
comment above a member reaches none of them.

```csharp
// Bad - the rationale is invisible to every caller
// Filters out entries that are blacklisted by the context, or relations of other entries.
private static void GetIgnoredEntities(...)

// Good - same sentence, now visible at every call site
/// <summary>
/// Filters out entries that are blacklisted by the context, or relations of other entries.
/// </summary>
private static void GetIgnoredEntities(...)
```

When you do write one, these apply:

- **`<summary>` is one sentence**, two at most. Do not restate the member name in prose. A summary that adds
  nothing is deleted, not kept for form's sake.
- **Skip the `Gets or sets the …` opener** on properties. It is four words of Microsoft house style before
  the first piece of information. Lead with the substance instead.
- **`<param>` is all-or-nothing per member.** `CS1573` fires when *some* parameters are documented and others
  are not. So either document every parameter or none. Prefer none, and reach for the full set only when at
  least one parameter needs a unit, a range, a null-meaning or an ownership rule.
- **`<returns>`** only when the return value is not implied by the method name and return type. Never
  `<returns>A new instance.</returns>`.
- **`<exception>`** for exceptions the caller is expected to handle.
- **`<inheritdoc />`** on implementations and overrides. Never copy an interface's documentation into its
  implementation — the copy goes stale on the first change to the interface.
- Reference types with `<see cref="..."/>` rather than a bare name, so the reference survives a rename.
- **Tests are exempt.** `CS1591` is suppressed for every `*Tests` project in `Directory.Build.props`, and a
  test's name carries its intent. Rationale about a counter-intuitive *setup* still belongs in `///` when it
  describes a helper member.

```csharp
// Bad - three tags, zero information beyond the signature
/// <summary>
/// Downloads and deserializes the module metadata JSON using the specified package information.
/// </summary>
/// <param name="package">The package descriptor identifying the module.</param>
/// <param name="cancellationToken">A token to monitor for cancellation requests.</param>
Task<ModuleMetadata?> GetModuleMetadata(ModuleDependencyPackage package, CancellationToken cancellationToken);

// Good - one sentence, and it is the sentence the caller needs
/// <summary>
/// Downloads and deserializes the module metadata, or <see langword="null"/> if the package carries none.
/// </summary>
Task<ModuleMetadata?> GetModuleMetadata(ModuleDependencyPackage package, CancellationToken cancellationToken);
```

### Markers

Use `// TODO:` and `// HACK:` only, each followed by an issue reference. `XXX`, `FIXME` and bare `TODO`
without a reference are not accepted — an untracked marker is a comment nobody will ever act on.

```csharp
// TODO(#1423): replace with the ordered outbox once the master-slave sequence lands.
```

### Razor

- `@* *@` only for a structural section label that the markup cannot express, e.g. `@* Will *@` separating a
  group of MQTT fields. Prefer extracting a named component.
- Put rationale in the `@code` block or the code-behind, not in the markup.
- No commented-out markup. See "Delete these comments" above.

### Tests

Beyond the `// Arrange`, `// Act`, `// Assert` markers, a test needs a comment only when the *setup* is
counter-intuitive; the test name carries the intent. The markers themselves are structure, not commentary —
see [Test Structure Guide → Arrange / Act / Assert](test-structure-guide.md#5-arrange-act-assert).

### Samples

Everything under `samples/` is teaching code, so comment it **more** than the rest. Explain the mechanics a
newcomer needs: how a message flows, why a call goes to one endpoint rather than another, what a framework
hook is for. "No need to explain the obvious" does not apply here — what is obvious to us is exactly what
the sample exists to teach. The form rules still hold, and a deliberately missing piece is described in
prose rather than left behind as commented-out code.
